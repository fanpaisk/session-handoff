## 1. `AGENTS.md`（项目根，自动加载）

**整个块必须包在幂等标记之间。** 交接职责的全部内容都放进 `<!-- SESSION_HANDOFF:START -->` 与 `<!-- SESSION_HANDOFF:END -->` 里：

- 标记已存在 → 只替换标记之间的内容，块外一个字都不动。
- 文件存在但无标记 → 整个标记块追加到末尾，不重排、不改写原有内容。
- `SESSION_HANDOFF:START` 在文件中必须**只出现一次**。

```markdown
<!-- SESSION_HANDOFF:START -->

## 开工前必读

进入本项目的每个新会话，在动手之前：

1. 读 `docs/STATUS.md`，复述：这个项目是什么、当前状态、下一步做什么。
2. 读 `docs/DECISIONS.md` 中与本次任务相关的条目。
3. 复述有困难的地方就是文档缺口：先向用户提问并补文档，不要猜。

## 项目定位

<一句话：这是什么，给谁用，解决什么问题。>

## 硬约束

- <不可违反的规则，例如「X 目录必须保持只读」>
- <技术栈、接口、兼容性或性能约束>

## 命令

- 构建：`<command>`
- 测试：`<command>`
- 验收：`<command 或检查步骤，以及预期输出>`

## 已知的坑

- <踩过的坑> —— 正确做法是 <...>。

<!-- SESSION_HANDOFF:END -->
```

**预算按整个文件计量，不按标记块。** 自动加载的是整个 `AGENTS.md`，所以真实成本是**文件总量**，不只是你写的那个块。

- 标记块自己 ≤ 60 行。
- **整个 `AGENTS.md` ≤ 一屏（约 60 行）。**

若项目原有的非交接内容把总量顶超了：这部分**不是交接职责，不擅自删改**。向用户报告总量与预算的差距，并建议拆到子目录 `AGENTS.md`（按目录就近加载，只在该子树工作时付费）或独立 skill。

块内内容超限时往下搬：
- 理由、权衡、被否方案 → `docs/DECISIONS.md`
- 长篇操作手册 → 一个独立 skill（正文按需加载，不进每轮上下文）
- 过程性知识 → 删掉

## 2. `docs/STATUS.md`（不自动加载，覆盖式更新）

```markdown
# 状态

最后更新：<YYYY-MM-DD>（<触发本次更新的任务>）

## 一句话状态

<这个工具现在处于什么状态——能不能用、能用到什么程度。>

## 交付物

| 交付物 | 状态 | 验收方式 |
|---|---|---|
| <功能 A> | 已验收 | `<command>`，预期 <...> |
| <功能 B> | 代码就绪（未实测） | 逻辑推演通过；用户尚未实测 |
| <功能 C> | 进行中 | 尚无可执行验收手段 |
| <功能 D> | 未开始 | — |

## 下一步

1. <下一个会话要做的第一件具体的事，具体到可以立刻开工>
2. <...>

## 未决问题

- <悬而未决的设计问题>：目前卡在 <...>，需要 <...> 才能推进。

## 已知缺陷

- <已知但不阻塞交付的问题>。
```

规则：
- **"验收方式"一栏不许留空。** 写不出可执行检查，状态就只能填"进行中"，不能填"已验收"。
- **"代码就绪（未实测）"是独立的一档。** 代码写完但没人真的跑过，既不是"已验收"也不是"进行中"；混为一谈会让下一个会话以为功能可用。
- **"下一步"必须是动作，不是方向。** "优化性能"不合格；"把 X 的 Y 从 N 降到 M，用 `command` 验证"合格。
- **不许写"见会话""见上文"。** 证据只在会话里时，要么把关键内容搬进来，要么标"证据未留存"并给出重验入口。会话一关，这种引用就静默失效——文件读起来却完全正常。
- **破坏性验证命令要写明恢复步骤**（如临时改配置跑完要还原），否则中途中断会留下错误状态。
- **说不清的写 `UNKNOWN`，别用"待定""再说"糊过去。** 格式：`UNKNOWN：<缺什么> —— <需要向谁确认>`。它是可检索的标记，交接报告里要逐条列出。
- 每次交接**整体重写**这个文件。它是快照，不是日志。

## 3. `docs/DECISIONS.md`（不自动加载，追加式更新）

```markdown
# 决策记录

追加式：每条只写一次，不改历史。决定被推翻时新增一条，并注明取代了哪一条。

## D-001 <决定的一句话概括>

- 日期：<YYYY-MM-DD>
- 决定：<做了什么。>
- 理由：<为什么。具体到能说服一个持怀疑态度的工程师。>
- 否掉的方案：<方案名> —— <为什么否掉。这条往往比"决定"本身更有价值。>
- 影响：<它约束了什么后续选择；要改它得付什么代价。>
```

规则：
- **涉及技术权衡的决定，"否掉的方案"必填。** 缺少它，下一个会话会重新提出你三周前已经否掉的方案，并且不知道为什么被否——这是最昂贵的重复劳动。
- **纯用户指令型决定不必硬凑备选方案**（例如"用户明确拒绝开机自启"）。这种情况写"用户指定／用户拒绝"即可。**不要为了填满格式而编造一个不存在的方案**——那正好违反"不许编造"。
- 理由要写到**能顶住质疑**。"这样更好"不合格；"因为 A 场景下 B 会失败，而 A 是主要用法"合格。
- 决定若源于**一次事故**，把事故本身写进理由（例如"贪心正则吞掉三个函数导致面板全空"）。事故是最有说服力的理由，也是下一个会话最容易重犯的错。
- **理由记不清就写 `UNKNOWN：理由 —— 需向用户确认 <什么>`。** 宁可留一个可检索的缺口，也不要写一个听起来合理但没有来源的理由——后者会被后续每个会话当成事实，而假前提会推导出真错误的决策。
- 只记**约束未来选择**的决定。纯粹的代码细节属于代码本身，不属于这里。

## 4. 填好的完整示例

项目：`logscope`，一个过滤 JSON 日志的命令行工具。场景是"`--where` 单条件过滤已验收，时间比较还没做"。

### `AGENTS.md`

```markdown
## 开工前必读

进入本项目的每个新会话，在动手之前：

1. 读 `docs/STATUS.md`，复述：这个项目是什么、当前状态、下一步做什么。
2. 读 `docs/DECISIONS.md` 中与本次任务相关的条目。
3. 复述有困难的地方就是文档缺口：先向用户提问并补文档，不要猜。

## 项目定位

logscope 是一个过滤 JSON 日志的命令行工具，给运维排查线上问题用：
输入日志流 + 一组过滤表达式，输出命中的行。

## 硬约束

- 必须能读 stdin 流式处理，不允许把整个输入读进内存——日志可能几十 GB。
- 输出字段顺序必须稳定，下游有 awk 脚本按列位取值。
- 只支持 Python 3.11+，不引入标准库以外的依赖（见 `DECISIONS.md` D-001）。

## 命令

- 测试：`pytest -q`
- 验收：`cat tests/fixtures/sample.jsonl | python -m logscope --where 'level=error' | wc -l`，预期 `7`

## 已知的坑

- 逐行 `json.loads` 遇到含未转义换行的日志会中断，必须用
  `json.JSONDecoder().raw_decode` 做恢复（`src/logscope/reader.py`）。
- `--where` 的时间比较不能按字符串比（见 D-003）。
```

### `docs/STATUS.md`

```markdown
# 状态

最后更新：2026-10-04（实现并验收 --where 单条件过滤）

## 一句话状态

能用：把 stdin 的 JSON 日志按 `--where` 单条件过滤后输出。
缺：时间比较、多条件组合。

## 交付物

| 交付物 | 状态 | 验收方式 |
|---|---|---|
| 流式读取 stdin | 已验收 | `python -m logscope < tests/fixtures/big.jsonl > /dev/null`，峰值内存 < 50MB |
| `--where` 单条件过滤 | 已验收 | `cat tests/fixtures/sample.jsonl \| python -m logscope --where 'level=error' \| wc -l` → `7` |
| `--where` 时间比较 | 进行中 | 尚无可执行验收手段 |
| 多条件组合 | 未开始 | — |

## 下一步

1. 让 `--where 'ts>2026-10-01T00:00:00Z'` 正确工作：把两侧解析成 datetime 再比较，
   用 `pytest -q tests/test_where_time.py` 验证。
2. 在 `tests/fixtures/sample.jsonl` 补一条带 `+08:00` 偏移的用例。

## 未决问题

- 多条件组合的语法：`--where A --where B`（隐含 and）还是 `--where "A and B"`？
  后者要手写表达式解析器。卡在不知道下游脚本怎么调用，需要向用户确认。

## 已知缺陷

- 每秒超过约 50 万行时输出会乱序（多进程缓冲未加锁）。不阻塞当前交付。
```

### `docs/DECISIONS.md`

```markdown
# 决策记录

追加式：每条只写一次，不改历史。决定被推翻时新增一条，并注明取代了哪一条。

## D-001 只用 Python 标准库，不引入第三方依赖

- 日期：2026-09-28
- 决定：只用 `json`、`argparse`、`sys` 等标准库。
- 理由：工具要能在客户的离线跳板机上直接跑，那里装不了 pip 包。这是硬需求，不是偏好。
- 否掉的方案：pandas —— 能把整个过滤写成一行，但跳板机装不上，等于工具交付不了。
- 影响：过滤逻辑和将来的表达式解析器都得手写，不能再考虑 lark / ply。

## D-002 输出字段顺序固定，不跟随输入顺序

- 日期：2026-09-29
- 决定：输出恒为 `ts, level, msg, ...其余原样`。
- 理由：下游有一个 awk 脚本按列位取值，输入顺序一变它就崩。
- 否掉的方案：原样透传 —— 更"忠实"，但会打破下游。
- 影响：新增字段只能追加到末尾，不能插在中间。

## D-003 时间比较必须先把两侧解析成 datetime

- 日期：2026-10-03
- 决定：`--where ts>...` 先把两侧解析成 datetime 再比较。
- 理由：字符串比较在带时区偏移的日志上是错的。`2026-10-01T00:00:00+08:00`
  按字符串排在 `2026-09-30T20:00:00Z` 之前，但它实际更晚。这会在生产排查时给出
  错误的答案——比直接报错更危险。
- 否掉的方案：字符串前缀比较 —— 快，但在带时区偏移的日志上会给出错误结果。
- 影响：每次时间比较要付解析开销；已决定不为它加缓存，因为内存约束优先。
```

### 这个示例里值得注意的地方

- **`AGENTS.md` 里没有一句会话过程。** 没有"今天调了三个小时"、没有时间线。只有每轮都需要付费的约束。
- **每条"已验收"都挂着一条能直接粘贴重跑的命令**，不是"测试通过"这种说法。
- **D-001 的理由是"客户跳板机装不了 pip"**，而不是"标准库更好"。这正是那种只存在于老会话里、不写下来就永久丢失的知识。
- **D-003 记录了为什么字符串比较是错的**（跨时区排序反了）。没有这条，下一个会话很可能"顺手优化掉"这个看起来多余的解析步骤。
- **未决问题写清了卡在哪里**（不知道下游怎么调用），而不是只写"待定"。
- **缺陷如实列出**（50 万行/秒乱序），尽管它不阻塞交付。隐瞒缺陷会让下一个会话在错误前提上做决定。
